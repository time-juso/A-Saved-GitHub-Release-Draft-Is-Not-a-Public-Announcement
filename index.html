A Saved GitHub Release Draft Is Not a Public Announcement

Saving a GitHub release draft preserves work for later; it does not establish that the announcement is available to ordinary readers. If you can see a release while signed in as a maintainer but a colleague cannot open it, check its state and the intended audience before sending the same link again. A convincing preview is not a reader-access test.

Consider a fictional volunteer project preparing a new edition of a community resource handbook. Priya has written release notes and attached a prepared file, then saved the release as a draft so another editor can review it. A workshop organizer asks for the announcement link. Priya should report that the release is awaiting review, not describe the draft as a completed public handoff.

Identify what has actually been completed

Begin with the smallest accurate statement. The notes may be written, the file may be attached, and an editor may be able to reopen the draft. Those are useful milestones. None answers the separate question of whether the intended readers can access the release and its materials.

GitHub's release workflow distinguishes Save draft from Publish release. Use that distinction in handoff messages rather than the vague word done. Priya can say that the draft is ready for editorial review and identify the remaining decision. The organizer can then plan around the real state instead of distributing a link that has not been checked for readers.

Do not infer release publication from the existence of a tag. Releases are based on Git tags, but a tag and a release are distinct records. A tag may already exist while release preparation continues. If someone points to a version label as proof that the announcement is ready, inspect the actual release state instead.

Keep the scope equally clear when talking about the handbook file. An attachment can be prepared before its content has been approved. A filename that includes a version number is a label, not evidence of editorial acceptance. Priya still needs the designated reviewer to confirm that this is the edition the project intends to distribute.

Review from the audience position

A maintainer's view can reveal material that another reader cannot see. GitHub's release-listing API, for example, includes draft releases only for users with push access. An authenticated result is therefore not sufficient evidence that a draft is available to the public. The account used for a check matters.

For a public repository intended for open readership, plan a signed-out browser check after authorized publication. For a private repository, use the intended authorized reader's access instead. Do not change repository visibility merely to make a test succeed. Publication state and repository access are different questions, and both must fit the project's intended audience.

If a colleague cannot open a link, ask what they were meant to receive before troubleshooting browser settings. Were they invited to review a draft, or were they expecting a public announcement? A review invitation may require project access. A public handoff should not depend on the sender's maintainer session.

For Priya's project, the immediate response is straightforward: the release remains a draft pending review. There is no reason to have the workshop organizer create an account, request broader permissions, or keep retrying an unverified link just to compensate for an unfinished publication step.

Finish the content review before the state change

Use the draft period to compare the announcement with what readers will actually receive. Read the release title, the short explanation of changes, and the attached handbook together. If the notes describe a corrected resource category but the file still contains the earlier wording, the release is not ready merely because the draft has saved successfully.

Check references according to their role. A project source, an external directory, and an individual resource page should not be described as though they carry the same authority. Priya's handbook can include routes for discovering websites while making clear that readers must assess the destinations themselves.

Record unresolved questions before asking for approval. A reviewer should not have to guess whether a missing attachment is intentional or whether a sentence still describes a proposed change. A short private review note can identify the exact file and the decision needed without adding operational clutter to the public announcement.

For repositories using immutable releases, complete the asset review before publication. GitHub documents restrictions on changing assets and the associated tag after such a release is published. Do not assume that replacing a mistaken file later will be a routine option. Check the repository's actual release settings and the project's process.

Make publication an explicit authorized step

Publication should follow the project's approval process, not a request to produce a shareable preview. Priya asks the responsible maintainer to confirm that the reviewed notes and file are the intended release. If the answer is still pending, leaving the release as a draft is the accurate outcome.

For an authorized maintainer, GitHub's documented browser path begins at the repository's Releases area. The release form provides Save draft for continued work and Publish release when ready to publicize it. Check that you are working on the intended release, especially when several drafts have similar titles.

Use this handoff sequence around that decision:

  1. Identify the exact draft and the edition it represents.
  2. Confirm that the notes and attached file have been reviewed together.
  3. Obtain the approval required by the project.
  4. Have an authorized maintainer perform the publication step.
  5. Test the resulting release from the intended reader's position.

Treat a pre-release label separately from draft status. A pre-release warns that an edition is not ready for production and may be unstable; it is not a substitute for keeping an announcement unpublished. Choose the state that matches the actual purpose instead of using similar-sounding labels interchangeably.

Verify the result before announcing availability

After publication, open the resulting reader-facing release page and inspect the title and notes. Follow the expected download route and check the received file. A page can be accessible while still carrying the wrong edition, so the access check should not end at the first successful page load.

For Priya's handbook, the organizer should be able to identify the edition, understand the relevant change, and obtain the intended document. Ask the organizer to confirm those specific observations if they are part of the handoff. A general reply that the link works gives less information than confirmation of the actual file.

Keep a brief completion record with the release page, the edition identifier, and the date of the reader check. Avoid recording an editor URL as the finished announcement. The useful record points a future maintainer to what readers were meant to see, not merely to the screen used while preparing it.

If the reader check fails, report the failure without widening access impulsively. The next step may be to correct a mistaken URL, finish a pending publication action, or resolve intended repository access. It is not automatically necessary to recreate the release, replace the file, or make a private project public.

Questions about release drafts and reader access

Does an existing tag prove the release is published

No. A tag identifies a point in repository history, while a release adds a separate publication record. Inspect the release itself and check its reader access. Do not use the tag's existence as a replacement for that verification.

Is a pre-release the same as a draft

No. Pre-release status describes the readiness of an edition; draft status concerns whether the release has been published. A project may publish a preview edition deliberately, but that is still a publication decision requiring the appropriate review and authorization.

Should I change permissions when someone cannot open it

Not until you understand the intended audience and the release state. A reviewer and a public reader may need different access. Confirm what the person should receive and follow the project's access policy rather than granting broader permissions as a shortcut.

Priya's announcement is ready to share when the approved release is published and the intended reader can obtain the correct handbook. Until then, calling it a draft gives collaborators the information they need to act without confusion.
